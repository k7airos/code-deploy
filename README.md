# Deploy

基于 Ink 8、React 和 `@inkjs/ui`，把本地目录 A 的内容发布到 SSH 服务器目录 B。一条配置可以写多个目标目录 B1、B2，同一份产物按顺序发布到每个目录。支持直接发布已有内容，或先执行自定义构建命令。工具不包含任何业务环境、服务器或分支预设；真实配置仅存用户目录。

## 安装

```sh
npm i -g @akairos/code-deploy
# 或
bun add -g @akairos/code-deploy
```

兼容 Node.js 22+ 与 Bun。`code-deploy` 的短命令为 `coded`，二者等价。

## 启动

需要 Node.js 22+（或 Bun）、pnpm、本地 `ssh`、`scp`、`tar`。启用 Git 检查或分支锁时需要 `git`。符号链接由 Node 检查，不依赖系统 `find`。远端需要 POSIX shell 和常用文件命令。

Windows：`ssh`/`scp` 需启用 OpenSSH 客户端（Win10 1809+，设置→应用→可选功能），`tar` 系统自带；构建命令通过 `cmd.exe` 执行。Ctrl+C 使用系统 `taskkill /T /F` 终止构建进程树，完成清理后才结束取消流程；macOS 使用进程组终止。密码认证在 Windows 未验证（Win32-OpenSSH 的 SSH_ASKPASS 支持不完整），建议使用 SSH 密钥或 agent。

```sh
pnpm install
pnpm build
npm link
code-deploy
```

TUI 使用左侧环境导航和主工作区。按 `n` 新建，`e` 编辑；配置表单左侧显示字段和草稿值，右侧编辑当前项。方向键、Tab 选择字段，Enter 编辑或切换开关，Ctrl+S 保存整份配置，Esc 取消当前编辑或丢弃草稿。表单超过窗口时滚动，已填内容保留且可以回看。输入 `/` 可使用 `/new`、`/config`、`/deploy`、`/check`、`/environments` 和 `/quit`。

「远程目录 B」一项可以填多个目录：每输入一个目录回车添加一次，输入框留空再回车才进入下一项；输入框为空时按退格删除最后添加的目录。目录不能重复或互为父子目录；不同源目录的锁定映射也不能绑定重叠的远程目录。

## 源目录与三个锁

实际源目录 A 是**启动工具时的当前目录**，工具不会隐式切换到另一个项目。`projectDir` 保存需要绑定的本地目录。

| 配置 | 开启后行为 | 默认 |
| --- | --- | --- |
| 锁定本地目录 | 当前目录必须等于配置的 A；子目录不算，真实路径相同的符号链接视为同一目录 | 关闭 |
| 锁定发布分支 | 当前 Git 分支必须等于 `expectedBranch`，否则直接拒绝 | 关闭 |
| 锁定映射关系 | 在 A 中显式开启，记录真实目录、当前分支、服务器及 B 的快照；发布时逐项匹配 | 关闭 |
| Git 状态检查 | 刷新上游引用，发现 Git 异常后等待明确确认 | 开启 |

三个锁独立配置。映射锁包含目录和分支的约束，即使另外两个开关关闭也会检查；锁定项不匹配时不能用确认警告绕过。修改映射绑定项前必须解除映射锁，修改后在正确目录和分支重新开启。用户配置内已开启的映射必须一一对应，同一个目录和分支不能绑定两个远程目标，同一个远程目标也不能绑定不同的目录和分支。服务器以配置中的 host、账号、端口识别；指向同一服务器的不同 SSH 别名不自动合并。

旧配置按此前行为迁移：开启目录锁；原来填写了分支要求的配置开启分支锁；Git 检查默认开启；原来的单个 `remoteDir` 迁移为 `remoteDirs` 列表。检测到旧单目录格式或旧映射快照时，默认关闭映射锁并清除旧快照，便于添加多个目标目录；确认目录后可重新开启映射锁。新版有效的映射锁不受影响，现有服务器、目录及密码来源继续保留在用户配置中。迁移结果在保存配置后写回文件。

## Git 检查与确认

正式发布前使用当前分支的 upstream 执行 `git fetch --no-tags`，不执行 pull、merge 或 checkout。检查暂存、未暂存、未跟踪文件，以及落后或领先上游的提交。无 Git 仓库、detached HEAD、缺少上游或 fetch 失败也会明确提醒，不能当作“干净且同步”。

有提醒时，在执行构建和上传前显示详情并等待 `[y/N]`；默认取消。TUI 可用 PgUp/PgDn 查看长提醒。确认后再次检查目录、分支、HEAD 和 Git 状态，发生变化时重新确认。构建结束、上传之前再次核验目录、分支和 HEAD，变化则拒绝。用户仍应避免在发布期间同时修改源文件。

```sh
code-deploy list
code-deploy example
code-deploy check example
code-deploy deploy example --yes
code-deploy config
code-deploy init /absolute/path/config.json
```

`--yes` 仅确认“开始发布”，不跳过 Git 异常确认。非交互执行遇到 Git 提醒时退出失败，不会构建或上传。`check` 会检查本地规则和 Git 状态，并只读列出远程目录；它可能 fetch，但不发布文件。

## 配置与密码

配置默认为 `~/.config/code-deploy/config.json`，权限 `600`；`CODE_DEPLOY_CONFIG` 可指定其他文件。项目内的 `config.example.json` 仅是虚构示例，不在启动时自动导入。首次可通过 `init` 导入；已有配置不会被覆盖。

`buildCommand` 留空表示跳过构建，否则通过本机 shell（macOS 为 `/bin/sh`，Windows 为 `cmd.exe`）在 A 执行用户信任的命令。`outputDir` 是 A 内的相对路径：`.` 表示 A 本身，`dist` 表示 A/dist。不要求 `index.html`，可以发布任意非空目录。直接发布 `.` 时会包含隐藏文件和 `.git` 等实际存在的内容，请选择真正需要发布的目录；本工具不内置排除规则。

默认使用现有 SSH 密钥 / Agent，沿用 `~/.ssh/config`。也支持配置密码环境变量名、在 TUI 中显式将密码保存到系统钥匙串，或直接在配置文件的 `password` 字段写明文密码（纯本地存储，文件权限 `600`，优先生效；不经过命令行参数或日志）。钥匙串条目绑定环境标识、服务器、账号及端口；修改目标后需要重新保存。Linux 无持久凭据服务时建议使用环境变量或 SSH 密钥。

## 发布方式

只构建一次、打包一次、上传一次，然后按配置顺序把同一份产物切换到每个目标目录 B1、B2……。上传临时压缩包后，在 B 同级目录完整解压，校验非空，然后把旧 B 改名为 `.<目录名>.backup-<uuid>`，再切换新 B。切换失败时尝试恢复旧目录，备份需要按需手工清理。使用同级锁目录避免本工具实例同时切换同一目标。

任一目录切换失败即中断整个发布，后面的目录不再处理；已切换的目录保留新版本，旧版本仍在同级备份中，可手工回滚。

这是目录整体替换，B 中原来存在的其他文件会进入备份而不进入新目录。目标需要至少两级绝对路径，不能是常见系统目录；目标及全部上级目录不能是符号链接，需填写真实路径。发布内容也不能含符号链接或 Windows junction。需要 B 的父目录写权限；两次重命名之间有短暂间隔，容器挂载点等特殊目录需先确认兼容。

压缩包上传到远端 `/tmp` 下权限为 `0700` 的独立临时目录。成功、失败或取消后均尝试清理；网络中断等导致清理失败时，会提示需要手工删除的路径。远端异常退出仍可能留下锁；取消后应确认实际版本。

## 验证

```sh
pnpm build
pnpm test
```

测试只使用临时目录、本地 bare Git 仓库和模拟 SSH，覆盖目录/分支/映射锁、旧配置迁移、Git fetch 与异常确认、完整发布、备份恢复、取消及 TUI 表单交互，不发布真实服务器。
